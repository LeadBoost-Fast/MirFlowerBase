# Mirflowers CRM: полный разбор проекта (для передачи другому ИИ)

Прочитай целиком, код изучать с нуля не нужно. Проверялись синтаксис (`node --check`) и работа в браузере (Chromium) с подставной базой по всем 6 ролям и вкладкам. С настоящим Firebase и на реальных телефонах не запускалось.

## 1. Что это
CRM-сайт цветочного магазина Mirflowers (Актау): заказы, склад, витрина, клиенты, чаты, график, отчёты, статистика сотрудников, финансы. Владелец хочет продавать систему другим бизнесам. Интерфейс на русском, светлая и тёмная тема, телефон и широкий экран.

Стек: один файл `index.html` в корне репозитория (~430 КБ, HTML+CSS+JS, без сборки, шаблонные строки), Firebase compat 12.19.0 (Auth, Firestore, Functions; до 7 ноября 2026 — 10.12.2). Проект Firebase: `mirflowersbase`. Cloud Functions на Node 22 (`firebase.json` → `runtime: nodejs22`). Сайт публикуется GitHub Pages из `main`; Firebase Hosting в `firebase.json` не настроен.

## 6. Новое в последней версии
### 6.1 Удаление
Кнопка «🗑 Удалить» (`delBtn`, показывается при `own()`, то есть владельцам) с подтверждением и записью в журнал: готовые букеты на витрине и в истории, каталог букетов, позиции склада, история склада, счётчик посетителей, заявки, сделки, карточка клиента (можно удалить и его заказы), диалог целиком, сообщения клиентов, сообщения командного чата, фото/чек/комментарий заказа, отчёты, записи журнала, точки. Логика в `delDoc`, `injDel`, `wrapDel`. В правилах удалять могут `isAdmin() || isOwner()`, остальным удаление запрещено.
«Очистка данных» в Профиле (admin и владельцы): выбор коллекций (массив `WIPE`, функция `wipeCol`), подтверждение словом УДАЛИТЬ.

### 6.2 Статистика (вкладка «Статистика»)
Одна карточка на сотрудника, флорист и оператор объединены («Флорист и оператор»). Считает `stCalc(id,a,b)`: собрано букетов (заказы + коллекция `builds` + витрина), принято заказов, принято оплат, приёмка чужих, взял в работу, возвращено на переделку, доставки, отчёты (чисто/не чисто, проблемы). Периоды: сегодня, 7, 30 дней, месяц (`stRange`, `stp`). Админы и владельцы видят всех и рейтинг, остальные только себя. Заказы считаются по последним 300.
**Сброс:** кнопка «🗑 Сбросить статистику» (admin и владельцы), два подтверждения: `confirm` и ввод слова СБРОС. В `settings/main` пишутся `statsFrom` (мс), `statsFromBy`, `statsFromByName`; `stCalc` считает только после `statsFrom`. Данные не удаляются; кнопка «Показать всю историю» обнуляет `statsFrom`.

### 6.2б Сброс финансов и аналитики
Только владелец и главный админ (`own()`). Кнопка «🗑 Сбросить финансы и аналитику» внизу вкладки «Финансы»: два подтверждения (`confirm`, затем выбор даты и ввод слова СБРОС). В `settings/main` пишутся `finFrom` (дата YYYY-MM-DD), `finFromBy`, `finFromByName`. Функция `fz` в `range()` (Финансы) и `apr()` (Аналитика) не даёт периоду начаться раньше `finFrom`. Данные не удаляются; «Показать всё время» обнуляет `finFrom`. По умолчанию дата = завтра (сегодняшние данные тоже скрываются). «Долги клиентов» по датам не фильтруются. Правила: запись в settings у владельцев и так полная, менять не нужно.

### 6.2в Резервная копия и экспорт
Профиль, блок «Резервная копия и экспорт» (`expCard`, admin и владельцы). «💾 Резервная копия (JSON)»: выбор коллекций (`EXPC`), опция «без фото», скачивается один файл `mirflowers-backup-ДАТА.json` (Timestamp превращаются в `{ts:мс}`, чаты идут вместе с сообщениями). CSV для Excel (разделитель `;`, UTF-8 с BOM): заказы (все, не только последние 300), клиенты, расходы (только владельцы). Расходы и закупочные цены в копию попадают только у владельцев. Действия пишутся в журнал. Автокопия по расписанию описана в 6.5.

### 6.2г Push-уведомления (когда сайт закрыт)
Технология: Firebase Cloud Messaging (веб-push). Файлы: `firebase-messaging-sw.js` (сервис-воркер, показывает уведомление из data-сообщения), `manifest.json` и иконки `icon-180/192/512.png` (для установки на экран «Домой», на iPhone push работают только так, iOS 16.4+), `firebase.json` (заголовок no-cache для сервис-воркера).
Клиент (`index.html`, блок «Push-уведомления»): карточка «Push на телефон» в Профиле (`pushCard`): включить/выключить, выбор типов (`PUSHEV`: ord, ready, courier, lead, chat, rep, remind), «Прислать проверку». Токен устройства хранится в `pushTokens/{токен}`: `uid`, `role`, `ev{тип:false}`, `ua`, `ts`. Ключ VAPID вставляет владелец в той же карточке (`settings/main.vapid`). При выходе токен удаляется, при входе другого пользователя токен переходит к нему (`pushSync`).
Сервер (`functions/index.js`): `pushNewOrder` (новый заказ), `pushOrderChange` (готов к приёмке, переделка, назначена доставка), `pushNewLead`, `pushClientMsg` (входящее сообщение клиента), `pushNewReport` (админам и владельцам), `pushReportReminder` (каждый день 20:00 Asia/Aqtau тем, кто по графику работал и не сдал отчёт), `pushTest`. Общая функция `push(type,who,msg,exclude)` выбирает токены по роли и настройкам, автору действия не шлёт, мёртвые токены удаляет. Если при деплое ошибка региона, задайте `OPT={region:"..."}` по региону Firestore.
Правила: `pushTokens`: сотрудник читает, создаёт, меняет и удаляет только свои токены (`uid == request.auth.uid`).
Деплой: `firebase deploy --only firestore:rules,functions` (нужен тариф Blaze; Cloud Scheduler включится сам). Старые уведомления внутри открытого сайта (`nf*`, `np_*`) остались и работают отдельно.

### 6.3 Отчёты (вкладка «Отчёты», карточка на главной)

Проверка: админы и владельцы принимают (`rp_ok`) или пишут замечание, видят блок «Сегодня не сдали отчёт» (`rpMissing`: по графику `shifts` с `t:"work"` и ролям assistant/florist/operator) и фильтр «⚠ Проблемы». Флаги `rpFlag`: ok / warn / bad.

### 6.5 Остатки, накладная с QR, статус для клиента, автокопия (итог)
**Работает без тарифа Blaze (Firestore + Hosting/GitHub Pages):**
- **Накладная с QR:** «🖨 Накладная» в карточке заказа (`o_print`), печать A5. QR ведёт на страницу статуса. Библиотека qrcode-generator 1.4.4 (cdnjs); без интернета печатается без QR.
- **Статус для клиента:** «🔗 Ссылка клиенту» (`o_link`). В заказ пишется `pub` (24 hex, случайный), в коллекцию `pubOrders/{pub}` копируются только `bn, st, dv, date, time, shop, phone`. Ссылка: `status.html?t=<pub>` (работает на любом статическом хостинге). Синхронизацию делает открытый сайт сотрудника (`pubAuto` после снимка заказов, поле `pubKey` на заказе); курьер не пишет в `pubOrders`, статус «Выдан» подтянется, когда сайт откроет сотрудник. Правила: `pubOrders` читается по `get` кому угодно, `list` запрещён, писать `isWork()`. «Повторить» заказ `pub`/`pubKey` не копирует. При удалении заказа документ `pubOrders` остаётся (удалить вручную).
- Остатки: поле «минимум» и пометка «Мало» в «Складе» уже были.
**Написано, но не включено (нужен тариф Blaze, Storage, `firebase deploy --only functions`):** в `functions/index.js` `pushLowStock` (push `stock`, включается в Профиле), `dailyBackup` (каждый день 03:00 Asia/Aqtau, JSON в Cloud Storage `backups/ГГГГ-ММ-ДД/`, 14 дней, статус `settings/main.lastBackup`, показывает `bkInfo()`), `backupNow` (кнопку `data-a="bk_now"` в `expCard` нужно вернуть, обработчик в коде есть). Пока ручная резервная копия JSON/CSV в Профиле.

### 6.6 Правки интерфейса (ноябрь 2026)
- **Окна:** у каждого модального окна есть ручка и крестик ✕, закрытие свайпом вниз (телефон) и клавишей Esc (`modal()`, `swipeClose()`).
- **Накладная:** открывается поверх страницы (`#wb`), кнопки «Закрыть» и «Печать», размеры A5, чек 80 мм, этикетка 58 мм (запоминается в `localStorage.wbsz`).

Главная флориста начинается со списка «Заказы к сборке», отсортированного по `mk`; новые заказы там принимаются кнопкой «На себя / в работу».
- **Витрина:** вместо чипа «Каталог букетов» кнопка «＋ Добавить букет» (вручную, из каталога, с необязательным списанием со склада). «Продать» показывает сумму и учитывает продажу в главной (сумма и число продаж за сегодня) и в «Финансах».

- **Точка:** при входе окно «Где вы сегодня?» (`#locgate`, `locGate()`). Выбор хранится в `localStorage.locSel` и сбрасывается в конце смены по графику (`locUntil()`), без смены в графике через 12 часов. «Все точки» могут выбрать только администраторы. У сотрудников с закреплённой точкой окна нет.

## 13. Правки 6 ноября 2026 (вечер): курьер, сборка, стабильность

### Курьер
- **Подтверждение в работу обязательно.** Назначенная или свободная доставка у курьера показывается кнопками «Принять в работу» и «Отказаться» (`curActs`). Пока курьер не принял заказ, кнопки «Доставлено» нет. «Взять доставку» (свободный заказ) сразу считается принятием, перед этим спрашивается подтверждение.
- В заказ пишутся `cAcc` (мс времени принятия), `cBy`. Админам и операторам в карточке: «курьер: имя, принял(а) в ЧЧ:ММ» или «ещё не подтвердил(а)». Оператор при «Передать курьеру» получает предупреждение, если курьер не принял.
- **Таймер 3 минуты:** кнопка «Доставлено» неактивна до `cAcc + 180000` (`cwait`, атрибут `data-cw`, обновляется раз в секунду). Логика `adv` проверяет время и без кнопки (обход через DevTools не работает). Это отдельный таймер от `wait()` (3 минуты после передачи курьеру для отметки оператором без фото).
- **Отказ от доставки** (`cur_rel`, `curRelForm`): окно с необязательной причиной. Пишутся `courier:""`, `cAcc:0`, `cRelAt`, `cRelBy`, `cRelNote`. Заказ возвращается в «Свободные», статус не меняется. Оператор видит строку «курьер … отказался» и получает уведомление (на сайте и push `ord`, функция `pushOrderChange`). Отменяется назначение курьера, а не сам заказ клиента.
- **Исправлено:** «Взять доставку» раньше переводила заказ из «Собирается» (1) сразу в «Готов» (2). Теперь статус заказа при взятии доставки не меняется.
- Все три действия курьера (взять, принять, отказаться) и отметка доставки выполняются в транзакции: два курьера не возьмут один заказ.

### Завершение доставки
- Фото вручения необязательно. Кнопка «Доставлено» открывает окно: либо выбрать/снять фото (отправляется сразу), либо нажать «Закрыть». В обоих случаях `st:4`, `doneAt`; без фото `proof:""`. Крестик ✕, Esc и свайп только закрывают окно, заказ остаётся «В пути». Повторное нажатие безопасно (проверка в транзакции).
- Для доставки статус 4 в интерфейсе называется «Доставлен» (`stL(o)`), для самовывоза остаётся «Выдан».

### Сборка и стабильность
- **«Начать сборку»:** `takeOrder` теперь в транзакции. Если заказ уже взял другой, сообщение «Этот заказ уже взял(а) …». Двойной клик не создаёт дублей.
- **Причина «кнопка не срабатывает»:** снимок базы приходил между нажатием и отпусканием пальца, страница перерисовывалась, кнопка заменялась новой, клик терялся. Теперь перерисовка (`dq`) откладывается, пока палец на экране (`pdn`), и пока вкладка скрыта; задержка 60 мс.
- `run()`: если предыдущее действие зависло (например, нет сети), блокировка снимается через 20 секунд, а повторное нажатие раньше показывает «Подождите…» вместо молчаливого игнора.
- Миниатюры фото грузятся лениво (`loading=lazy`, `decoding=async`).
- **Не исправлено (корневая причина тормозов):** фото хранятся в документах заказов (base64) и все 300 последних заказов с фото приходят на каждый телефон при каждом изменении. Решение: вынести фото в Firebase Storage (нужен тариф Blaze) и хранить в заказе только ссылку.

### Правила и функции
- `firestore.rules`, заказы: курьер может взять свободный заказ (без смены статуса), подтвердить свой, отказаться от своего; «Доставлено» разрешено только после подтверждения (`cAcc > 0`), `proof` может быть пустой строкой.
- `functions/index.js`: push операторам и владельцам при отказе курьера.
- Деплой: `firebase deploy --only firestore:rules,functions`. Правила обязательно выкладывать вместе с сайтом, иначе у курьеров будут ошибки доступа.
- Проверялось: `node --check`, браузер (Chromium, подставная база, телефонный экран, роли оператор, флорист, администратор, 2 курьера). С настоящим Firebase и правилами (эмулятор) не запускалось.


## 14. Правки 6 ноября 2026 (ночь): язык RU/KZ, флорист: подтверждение и передача заказа

### Язык (Русский / Қазақша)

- Устройство: код в интерфейсе остаётся русским, казахский подставляется словарём. `KZ` (точное совпадение строки) и `KZR` (шаблоны с подстановкой имени и времени), функция `t(s)`. Для казахского включается `MutationObserver`, который переводит текст, `placeholder`, `aria-label` и `title` на странице; `toast`, `confirm` и `alert` тоже проходят через `t`.
- Стиль казахского: разговорный, с заимствованиями (заказ, доставка, сборка, склад). Примеры из ТЗ внесены дословно («Работаға алу», «Сборканы бастау», «Басқа флористке беру», «Бул заказды [Имя] алып қойды», «Инет жоқ. 20 сек күте тұр.», «Күте тұр...»).
- Чтобы перевести новую строку: добавьте пару в `KZ` (или шаблон в `KZR`). Строка, которой нет в словаре, остаётся русской. Перевод покрывает вкладки, статусы, кнопки курьера и флориста, основные сообщения; остальные экраны (финансы, отчёты, настройки магазина и т.д.) переведены не полностью. Перед запуском текст стоит показать носителю языка.
- Нет интернета: `run()` не запускает действие и показывает «Нет интернета. Подождите 20 сек.»; ошибки Firestore `unavailable` и `deadline-exceeded` показывают то же.

### Флорист: подтверждение «Начать сборку»
- Кнопка открывает окно «Точно берешь этот заказ?» с «Да» / «Отмена» (`takeConfirm`), и только после «Да» вызывается `takeOrder` (транзакция). Окно показывается всем, кто нажимает «Начать сборку» (флорист, помощник, оператор, админ).

### Флорист: передача заказа (двойное подтверждение)
- Кнопка «Передать заказ» (`xfBtn`) на карточке и в окне заказа: только у флориста или помощника, который взял заказ (`takenBy`), пока статус 1 (Собирается) и передача не идёт. Список получателей: активные флористы и помощники, кроме себя и владельцев (`xfWho`).
- Поля заказа: `xfSt:"wait"`, `xfTo`, `xfFrom`, `xfAt` (мс). Пока передача идёт, на заказе плашка «Ожидает подтверждения передачи · А → Б», кнопка «Готов» блокируется (для всех).

- Таймаут 1 минута (`XF_MS`). Состояние выводится по времени (`xfPend`): по истечении минуты заказ считается снова за отправителем, даже если запись ещё не сделана. Чистку полей делают браузеры отправителя и получателя (`xfExpire`, раз в секунду). Если оба офлайн, поля почистятся при их следующем входе. Запоздавший ответ получателя отклоняется (допуск 5 с на разницу часов).

- `functions/index.js`, `pushOrderChange`: push получателю при начале передачи (тип `ord`, текст пока только на русском).
- `firestore.rules` не менялся: поля `xf*` и `takenBy` уже разрешены ролям `isWork()`. Как и запрет «принять свой заказ», защита от обхода работает только в интерфейсе и транзакциях клиента.

### 14.2 «messaging/failed-service-worker-registration» при вызове функций (6 ноября 2026)

Причина: SDK функций при разрешённых уведомлениях сам запрашивает токен messaging и регистрирует сервис-воркер в корне домена, а сайт лежит в папке (GitHub Pages).

- Если функции не развёрнуты (`firebase deploy --only functions`), удаление сотрудника по-прежнему удаляет только профиль, аккаунт входа убирается вручную в Firebase → Authentication.

## 25. Права в правилах и полная история заказов (7 ноября 2026)
**Права (`firestore.rules`, функция `orderMarksOk()` для `orders` update; то же проверяет сайт):**
- Отметки пишутся только от своего имени: `paidBy`, `accBy`, `asm` = свой uid или пустая строка (сброс при переделке); `takenBy` = свой uid, и только у нового заказа (`st` 0), заказа без `takenBy` или при передаче, адресованной мне (`xfTo`). Админ и владельцы могут всё.
- «Готов» (`asm` = я) на заказе, который взял другой флорист, — только админ и владельцы (раньше проверял только сайт).
- Приёмка своего заказа (`rv`: `wait` → `ok`, где `asm` = я) — только админ и владельцы. На сайте проверка была мёртвой (`!isDirect()` всегда ложно) — теперь `!adm()`.
- Создание заказа: `by` и `paidBy` (если есть) — только свой uid.

**История заказов (`index.html`, рядом с `RAW`):** подписка по-прежнему держит 300 последних (`O`, их число `ON`). Если заказов 300 и больше, вкладки догружают заказы за выбранный период одним запросом и кладут в `OX` (Map по id); свежая версия всегда из `O`.

- `oH()` = `O` + история с фильтром точки, `oHr()` = то же без фильтра (вместо `RAW[0]` в аналитике).
- **Неоплаченные** (7 ноября 2026): когда заказов 300+, у `mgr()` включается живая подписка `where("paid","==",false)` (`upSub`, флаг `UPON`), документы идут в `OX`; оплаченный (ушёл из выборки) перечитывается. Через `oH()` считаются «Не оплачено» на главной, «Долги клиентов» и «Неоплаченных заказов» в Финансах, строка «готово, но не оплачено» в «Сейчас нужно» и фильтр неоплаченных в Заказах. Отменённые неоплаченные тоже приходят в подписку (без составного индекса их не отсечь), в расчётах они исключаются.

- Индексы не нужны (одно поле). Стоимость: чтение каждого заказа периода один раз за сессию.
- Проверено в эмуляторе (300 свежих + 120 старых заказов, 60 старых не оплачены): долги 60 000 ₸ и 60 неоплаченных в списке (раньше 0), клиентов 121, Финансы за всё время 420 заказов и верная выручка, Аналитика за 30 дней без старых, повторная перерисовка не делает новых запросов.

Главное было не в расчётах, а в том, что браузер на каждое изменение базы выбрасывал и строил заново всю страницу (`innerHTML`), плюс дорогие форматировщики дат и денег.
- **`morph(el,html)`** (начало скрипта): новая разметка разбирается в `<template>` и сравнивается с текущей; меняются только отличающиеся узлы, атрибуты и тексты; одинаковая разметка — страница не трогается (`el.__h`). Фокус, выделение, прокрутка, набранный текст в полях сохраняются (у активного поля значение не перезаписывается). `draw()` использует `morph` для `#v` и `nav`; при смене вкладки и на вкладке «Карта» (туда переносится элемент карты `GMEL`) — прежний `innerHTML`. Узел с атрибутом `data-nomorph` заменяется целиком. Обработчики кликов и так на `document` (`data-a`), `bind()`/`chBind()`/`tcBind()` ставят `on*`-свойства — повторный вызов безопасен.
- **Кэш `Intl.DateTimeFormat`**: `Date.prototype.toLocaleDateString/TimeString/String` обёрнуты (кэш по локали и параметрам, те же умолчания, что у браузера; неверная дата — как раньше). Деньги: `M`/`kf` через один `Intl.NumberFormat("ru-RU")` (`NFR`).
- **Казахский**: в `morph` перевод (`window.trN`) делается на шаблоне до сравнения, записи наблюдателя после `morph` сбрасываются (`window.trObs.takeRecords()`), `t()` запоминает результаты (`TC`, до 5000 строк; уже переведённая строка помечается, чтобы не разбирать её снова).
- **Чат команды**: снимок `team` зовёт `dq()` вместо немедленного `draw()`.
- **`clients()`** запоминает результат, пока не изменились заказы (`ORV`), история (`OXV`), клиенты (`CU`) и точка.
- **CSS**: `#v .oc` и строки `.todo` с `content-visibility:auto` — карточки за экраном не раскладываются (iOS 18+, на старых просто игнорируется).
- Проверено после правок: форма заказа (ошибки полей), чат (кнопки, поле над панелью), история/долги/клиенты, казахский текст после изменения заказа, поиск в Заказах держит фокус и текст при наборе; ошибок JS нет.

## 29. Кнопки не ждут сервер, long polling (7 ноября 2026)
Владелец: зависают и «Начать сборку», и «Оплачено»; после перезахода работает, потом «тупеет». Диагностика: интернет есть, IndexedDB в порядке, сервер не отвечает даже после переподключения.
- **Связь — long polling**: `db.settings({experimentalForceLongPolling:true})` вместо `experimentalAutoDetectLongPolling`. Каждый обмен — отдельный короткий запрос; потоковое соединение, которое выбирал автовыбор, на iPhone/Safari со временем застревало.
- **Записи не ждут сервер** (обёртка сразу после `db.settings`): `DocumentReference.set/update/delete`, `WriteBatch.commit` и `CollectionReference.add` (теперь `doc()` + `set`, id создаётся на телефоне) ждут ответ сервера не дольше 1,5 с. Ответил — как раньше (ошибка правил видна сразу). Не ответил — действие считается выполненным: изменение уже применено в кэше Firestore на телефоне и уйдёт в фоне; поздняя ошибка сервера показывается сообщением (Firestore сам откатывает изменение), если у промиса не стоит `.own`. Исходный промис сервера — `.server`.
- **`pendWatch()`**: после такой записи ждёт `db.waitForPendingWrites()`; через 6 с — `netKick`, через 15 с — плашка сверху `#pendb` «Изменения ещё не отправлены на сервер. Они сохранены на телефоне.» с кнопкой «Перезагрузить»; плашка исчезает, когда сервер всё принял. Изменения переживают перезагрузку (очередь записей Firestore в IndexedDB).
- **«Начать сборку» без транзакции** (`takeOrder`): транзакции обязательно нужен сервер. Проверка по кэшу (`st` 0), затем обычный `update`; двойное взятие отклоняют правила (`orderMarksOk`: `takenBy` себе — только у нового/свободного заказа или при передаче мне). Отказ — «Этот заказ уже взял(а) …». Админ и владелец правилами не ограничены (могут перехватить). Остальные транзакции (склад, витрина, курьер, передача) не менялись.
- Проверено в эмуляторе: связь мертва и через 3 с восстанавливается — кнопка срабатывает через 1,5 с (было 6,1 с в PR #16, до него — никогда), сервер получает изменение через 6,8 с; связь мертва совсем — через 15 с плашка, после перезагрузки (кэш включён) изменение дошло до сервера; два флориста одновременно жмут «Начать сборку» (настоящие правила, 3 раунда) — заказ всегда у одного, второй видит «уже взял другой сотрудник». Форма заказа, чат, история/долги — без изменений.

## 33. «already-exists»: испорченный кэш Firebase на телефоне (7 ноября 2026)
- Владелец, 17:06, телефон 1: вкладка «Чаты» — «Нет доступа к чатам, код already-exists», при создании заказа «Сообщения: Ошибка: already-exists». Это внутренняя ошибка Firestore «Target ID already exists» — сбой учёта подписок; после неё подписки не получают данные, связь ведёт себя непредсказуемо. В эмуляторе не воспроизводится (40 циклов переподключений, проверок сервера и открытий/закрытий чата — без ошибок). Вероятно, кэш на телефоне испорчен — в том числе после смены режима вкладок (разд. 31) поверх старого кэша; перезагрузка не помогает, потому что кэш хранится на телефоне. Возможно, той же природы и прежние зависания.
- **Обнаружение**: обёртка `onSnapshot` (запросы и документы) ловит ошибки подписки `already-exists`, `internal`, `data-loss` → `fsReset`.
- **`fsReset(why)`** (не чаще раза в 10 мин): неотправленные заказы (`_pend`) откладываются в `localStorage.fsStash`, флаг `fsReset`, диагностика `kind:"cache-reset"`, перезагрузка. **`FSREADY`** при запуске: если флаг стоит — `db.clearPersistence()` до запуска Firestore, затем `enablePersistence`; `auth.onAuthStateChanged` ждёт `FSREADY`. **`fsAfterOrders`** после первого снимка заказов: отложенные заказы записываются на сервер (`set(..., {merge:true})`, запись в Журнал «Заказы после очистки кэша отправлены»).
- **Разовая очистка на каждом устройстве** (`CACHE_V="2"` в `localStorage.cacheV`): после первого снимка заказов, если кэш включён, — одна перезагрузка с очисткой старого кэша (застрявшие заказы при этом отправляются заново).
- `srvProbe` проверяет сервер документом без подписки (`pubOrders/__probe__`), а не `settings/main`, на который есть подписка.
- Проверено в эмуляторе: первый запуск — ровно одна очистка, дальше без перезагрузок; застрявший заказ + сбой подписки → очистка кэша → заказ на сервере и в списке; форма (без кэша) — 2 заказа без дублей; два флориста — 3/3; долгая сессия — 23/23.
- Тесты: в обычных проверках разовая очистка пропускается, отключение кэша — заменой `pre.then(()=>db.enablePersistence(...))`.

## 34. Режим «только сервер»: без кэша на телефоне (7 ноября 2026)
- Владелец работал в двух окнах сайта на одном телефоне и хочет, чтобы каждый аккаунт работал сам по себе, а данные были на сервере, а не на телефоне. Причины зависаний — в кэше Firebase на телефоне: в режиме нескольких вкладок с сервером говорит одна «главная» вкладка, а если она уснула в фоне (iOS), изменения из других не уходят; после смены режима старые и новые вкладки на одном кэше дали «already-exists».
- **Кэш выключен**: Firestore работает в памяти, каждая вкладка и каждый телефон берут данные прямо с сервера и не зависят друг от друга. `FSREADY`: `enablePersistence` вызывается, только пока `localStorage.cacheV` не `"3"`.
- **Переход без потерь** (`CACHE_V="3"`): при первом запуске новой версии старый кэш открывается, после первого снимка заказов неотправленные заказы откладываются (`fsStash`), `fsReset("to-server", force)` → очистка кэша → режим «только сервер» → отложенные заказы отправляются.
- Без кэша неотправленные изменения живут в памяти: через 20 с — сообщение «Нет связи с сервером: изменения ещё не сохранены. Не закрывайте сайт…», `beforeunload` предупреждает при закрытии. Тихая автоперезагрузка при застрявшей записи отключена (`PERSIST_OK=false`), иначе потеря. Внутренний сбой Firestore → `fsReset` (заказы откладываются и отправляются после перезагрузки).
- Цена: первое открытие грузит данные с сервера, а не из памяти телефона (при текущем объёме незаметно).
- Вход один на браузер: вкладки одного браузера — один аккаунт (так устроен Firebase Auth). Разные аккаунты на одном телефоне — Safari и иконка на экране «Домой» (у них раздельное хранилище) или разные устройства.
- Проверено в эмуляторе: заказ, застрявший в старом кэше, после обновления — одна перезагрузка, режим «только сервер», заказ на сервере ровно один раз; вторая вкладка видит заказ первой сразу; без связи — предупреждение через 20 с, после восстановления заказ на сервере и во второй вкладке; форма, два флориста, долгая сессия (23/23, медиана подтверждения 49 мс) — без замечаний.

## 40. Записи через REST вместо канала записи Firestore (7 ноября 2026)
- Владелец: опять зависание. Проверка связи показала `FIRESTORE (12.19.0) INTERNAL ASSERTION FAILED: Unexpected state (ID: da08)` — **без кэша**. По исходнику SDK 12.19.0 (`PersistentWriteStream.onFirst`): `hardAssert(!responseProto.writeResults || responseProto.writeResults.length === 0, 0xda08)` — первым ответом канала записи (рукопожатие) пришли результаты записей, то есть ответы старого и нового соединения перемешались (повтор/задержка запросов долгого соединения сетью или прокси, например iCloud Private Relay). После такого сбоя Firestore на странице мёртв. В эмуляторе не воспроизводится (565 и 380 записей под нагрузкой — 0 сбоев): нужна реальная сеть.
- **Все записи идут через REST** `documents:commit` (обычный запрос — ответ) — переопределены `DocumentReference.set/update/delete` и `WriteBatch.set/update/delete/commit` (поверх них — прежняя обёртка «не ждать дольше 1,5 с»). Канал записи SDK (`/Write/channel`) не открывается вовсе; чтение и живые обновления — по-прежнему SDK (long polling), транзакции — SDK (одиночный commit RPC, не канал записи).
- Кодирование: `fsVal` (null, bool, int/double, string, Date/Timestamp, массивы, map), `fsSplit`/`fsSplitDeep` (поля, `updateMask` для update и set merge — по листьям, `updateTransforms`: serverTimestamp → REQUEST_TIME, increment, arrayUnion → appendMissingElements, arrayRemove → removeAllFromArray; delete поля — путь в маске без значения), update — `currentDocument.exists`. Значения-заглушки FieldValue распознаются по `_methodName` (в сжатой сборке имена `_operand/_elements` переименованы, поэтому число/массив ищутся среди значений объекта).
- `fsCommit`: токен входа (`getIdToken`), таймаут 15 с, повтор при сетевой ошибке, 5xx, unavailable/aborted/deadline/resource-exhausted/internal (до 10 мин, задержка 0,8→15 с), при unauthenticated — обновление токена; отказ правил — ошибка сразу (коды как у SDK: permission-denied и т. д.). Счётчик `RQ` и `rqIdle()` заменили `waitForPendingWrites` в проверке связи и в `pendWatch`.
- Цена: без мгновенного «локального» отображения — экран обновляется, когда сервер разошлёт изменение (в эмуляторе ~50 мс).
- Тесты: в обвязках `window.__FSREST="http://127.0.0.1:8080"` (REST эмулятора).
- Проверено в эмуляторе: создание заказа, тройное нажатие, связь пропала/вернулась — запись дошла через 1 с, без дублей; два флориста — заказ у одного (правила отклоняют второго); два аккаунта 2 мин — подтверждение ~40 мс, второй видит ~50 мс, 0 перезагрузок; значок чатов; нагрузка 60 с — 1644 REST-записи, 0 соединений канала записи, 0 внутренних сбоев.
